# Scale results

Measured with `tests/e2e/scale.mjs` (import + browsing) and `tests/e2e/memory.mjs` (renderer memory without a debugger attached) against a 15,500-item library. Raw numbers: `test-data/scale-run/results.json` after a run.

## Setup

| | |
|---|---|
| Machine | Linux container, 4 vCPU, 16 GB RAM, no GPU |
| Display | Xvfb — **software rendering and compositing** (no GPU raster) |
| App | Production build (minified, React production), window 1440×900 |
| Image library | sharp **WebAssembly** build (Linux only — see README › Known limitations) |
| Library | 15,300 unique JPEGs (1600×1200 / 1200×1600, EXIF dates over 10 years, 6 camera models, ~30–40 KB each) + 200 short H.264 videos, in Year/Month-Event folders. Generated by `scripts/make-scale-media.mjs 15300 200`. Imported as *Keep in current location*. |

The functional suite (`tests/e2e/functional.mjs`, ~50 checks) covers the small-library case (~35 mixed items: every format, broken files, duplicates). 1,000 and 5,000 items were not run as separate tiers: the UI only does work for what's on screen, and import cost is linear in item count, so 15,500 is the stress case for both.

## Import (15,500 items, from drop to done)

| Metric | Result |
|---|---|
| First items visible after the drop | **1.4 s** |
| All 15,500 items browsable (dates, sizes, layout) | **48 s** (~320 items/s) |
| All thumbnails + metadata finished | 7 min 12 s (36 items/s) |
| UI frame times while idle during processing (avg / p95 / max) | 16.7 / 16.7 / 33.3 ms |
| Scrolling while files are still being added (avg / p95 / max) | 37 / 83 / 83 ms |
| Scrolling while thumbnails generate (avg / p95 / max) | 23 / 50 / 83 ms |
| Full 15k layout query while the workers are busy | 163 ms |

Thumbnailing is the slow phase, and it runs in the background with visible items first. 36 items/s is with the WebAssembly libvips build Linux needs. Native libvips (used on Windows and macOS) measured ~2.3× faster in the worker harness, which projects to roughly 3 minutes for the same set. That figure is an estimate, not measured on those OSes.

## Browsing (cold start with 15,500 items)

| Metric | Result |
|---|---|
| Launch → first thumbnails painted | **0.8 s** |
| Load the whole 15.5k layout (round trip / SQL) | 77 ms / 30 ms |
| Search, as you type (round trip) | 4–27 ms — e.g. `beach` 23 ms (1,351 hits), `2019` 18 ms, `june` 16 ms, `canon` 20 ms, `portrait` 27 ms (3,360), `img_0123` 10 ms |
| Fetch details for 400 items | 131 ms |
| Steady scroll, grid, 2,000 px/s (avg / p95 / max frame) | **16.6 / 16.8 / 16.8 ms** — locked 60 fps |
| Stress sweep: whole library top→bottom→top in 5 s (~6,000 items/s) | grid 34 / 83 / 183 ms · masonry 25 / 50 / 200 · timeline 38 / 83 / 217 · list 33 / 50 / 133 |
| DOM cells alive during the sweep | 42–65 (virtualized) |
| Viewer → next photo, full resolution on screen (median / max) | **5 / 15 ms** (neighbours are preloaded) |

The stress sweep moves far faster than anyone scrolls or drags the scrollbar. Its long frames are software rasterization of brand-new thumbnails, and should drop with GPU raster on real hardware.

## Memory

Renderer process, measured by `tests/e2e/memory.mjs` over a bare DevTools socket (Runtime domain only):

| | Resident | Private |
|---|---|---|
| After launch | 188 MB | 46 MB |
| After sweeping all 15,500 thumbnails through grid, masonry, timeline and list | 550–690 MB | 336–396 MB (flat across layouts — bounded, not growing) |

Chromium memory-infra breakdown after browsing:

- App heaps are small: Blink DOM heap 8 MB, V8 10 MB, Blink resource cache 2 MB.
- Decoded-image cache: 138 MB. This is Chromium's discardable memory; it is budget-capped and purged under memory pressure.
- malloc: 57 MB.
- Raster tiles: ~155 MB of shared memory, mapped into both the renderer and the GPU process (counted in both resident totals).

> **Why `scale.mjs` reports higher memory.** Playwright enables the DevTools Network domain, which keeps every response body (every thumbnail) alive inside the renderer. Its numbers are labelled "Playwright-attached" and should not be read as what a user sees.

## Fixed because of these runs

- **Crash at ~8,000 items on Linux** (SIGTRAP): Electron's glib collides with sharp's bundled glib. Fixed by switching Linux to sharp's WebAssembly build; details in the README.
- **Import throughput**: originally 22–44 items/s to browsable. Fixed by reading dimensions, orientation and EXIF date straight from file headers (JPEG/PNG/GIF/WebP) and by probing in parallel across the worker pool. Now ~320 items/s.
- **Renderer churn during import**: library-change events throttled while importing; item details refresh in place instead of flashing placeholders.
- **Production bundle**: shipped React's development build unminified (1.1 MB). Now production React, minified (497 KB), with a Content-Security-Policy.
- **Viewer flash**: for one frame after ←/→, the previous photo could appear in the new photo's frame. Fixed, and preloaded neighbours now appear on the first frame.

## Caveats

- **Software rendering only.** No GPU was available. On real hardware, GPU compositing makes scrolling cheaper, and Windows and macOS use native libvips.
- **Small synthetic JPEGs** (~35 KB versus 3–10 MB for real camera files):
  - The "browsable" phase reads only file headers, so it should stay in the same range on a local SSD.
  - Thumbnail generation decodes whole images, so on real photos it will be slower than measured here. Treat 36 items/s as an upper bound for Linux.
- The short test videos understate the cost of video poster frames and storyboards for long clips.

## Reproduce

```bash
node scripts/make-scale-media.mjs 15300 200
npm run build
xvfb-run -a node tests/e2e/scale.mjs              # import + browse (REUSE=1 skips the import)
xvfb-run -a node tests/e2e/memory.mjs             # renderer memory without Playwright (TRACE=1 adds the allocator breakdown)
```
